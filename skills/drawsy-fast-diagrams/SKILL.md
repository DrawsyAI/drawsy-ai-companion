# Drawsy Fast Diagrams

Use this skill only for Fast Mode canvas diagram work.

- Read the current canvas and call `get_canvas_capabilities`. When present, treat `diagramCode.nativeEditableTypes` and `diagramCode.sourceMaxBytes` as the converter's runtime authority. Choose Mermaid syntax from the request's meaning and actual support; do not use a fixed intent-to-family mapping or prescribe a visual style. Keep the user's facts, supplied numbers, canvas context, and existing visual language intact. Never invent data to force a chart.
- The current converter has editable native handlers for flowchart/graph, packet, architecture, ER, use case, mindmap, tree view, XY chart, pie, radar, and Sankey families. The installed parser may accept more syntax and render it as an image. Check `outputKind` (`editable-vector` or `image-fallback`) and `diagramType`; do not promise that fallback content stays editable. Mermaid's official syntax references follow `https://mermaid.js.org/syntax/<diagram-name>.html`; documentation can describe newer syntax than Drawsy's bundled parser.
- Use `render_diagram_code` to create a whole diagram. Fast Mode still supports normal canvas management: use `apply_canvas_changes` to update existing elements or delete existing elements, including failed or intermediate work you created; never delete unrelated content. Use `create_or_update_connector` and `set_container_label` for existing objects, and image insertion/replacement, canvas capture, and live preview when requested. The runtime checks raw upserts against the live canvas; never use them to create new shapes or diagram structures. The diagram result includes `outputKind`, `diagramType`, `elementCount`, inserted `elementIds`, and `bounds`; use those IDs and bounds to review the inserted group.
- Do not use native pointer gestures or another canvas path to bypass the diagram converter when creating a whole diagram. Preserve the user's visual choices when managing existing content.
- A syntax correction is for a request that failed conversion: make at most one focused correction and retry with a new `operationId`; reuse an id only to retry the same unchanged request. A post-render correction follows a successful conversion after inspection: read the canvas again, make a focused correction, and set `replaceOperationId` to the prior successful operation id so only that converter-created group is replaced.
- After rendering, inspect returned result details and the canvas layout. Capture the rendered area when visual verification matters. If inserting multiple diagrams, re-read and inspect placement before planning the next insertion. Rendering success does not prove that all requested meaning is present. If a focused post-render correction is needed, regenerate once using a new `operationId` and `replaceOperationId` set to the prior successful operation id; this replaces only that Fast-generated group. If the result remains misleading or the converter cannot represent the request faithfully, stop and explain the limitation or offer a meaning-preserving supported alternative.
